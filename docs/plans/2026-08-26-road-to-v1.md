# Road to v1.0

Tier: T4 (strategic scope definition — not an implementation plan)

**Status: ANALYSIS. Nothing here is approved for implementation.**

## What v1.0 should mean

Not "every Phase 6 item is done" — that list is 25+ entries and several are research, not
engineering. A defensible v1.0 is narrower:

> A stranger can install OmniScribe with one documented command, point it at a video, and
> get a good transcript — without reading the source, and without hitting a crash or a
> wall of junk segments. The output schema is stable enough to build against.

By that definition the *engine* is close to ready (Phases 1–5 complete, 604 tests, 98.4%
coverage) and the *product* is not. The gaps below are grouped by whether they block that
sentence.

---

## Tier 0 — v1.0 is impossible without these

### 1. The name is taken on PyPI, and the install docs are wrong today

`pip install omniscribe` installs **a different project**: *SoberMind Offline Session
Transcriber* (v0.0.5, uploaded 2026-05-30). Confusingly it is also a Whisper-based
transcription tool, so a user may not realise they got the wrong software.

Consequences:
- `README.md:36` currently instructs an install that yields someone else's package.
- This project **cannot publish under `omniscribe`**. `omni-scribe`, `omniscribe-cli` and
  `omniscribe-video` are all free on PyPI.
- The comment posted to issue #77 today recommends `uv pip install --upgrade omniscribe`.
  That is wrong and needs correcting on the issue.

Decision required: pick a distribution name. The import package (`omniscribe`) and the CLI
command can stay as they are — only the PyPI distribution name must change — but a
mismatch between `pip install X` and `import omniscribe` is itself a UX cost worth
weighing against renaming wholesale.

### 2. Nothing publishes anything

`.github/workflows/` contains only `ci.yml`. There is no publish workflow, no `build`, no
`twine`, no `PYPI_*` secret, no release automation, and no container registry push — the
Dockerfile is `docker build` only, and even a Docker CI build job is itself an open item.

v1.0 needs: a tag-triggered publish workflow, a published image, and an install path that
is verified in CI rather than asserted in the README.

## Tier 1 — "complete application" essentials

### 3. The headline feature produces visible junk on common input

The single entry under README "Known Limitations" is OCR noise on text-heavy backgrounds:
varying per-frame detections defeat cross-frame dedup, survive the frequency filter, and
yield *"dozens of sub-second `[ON-SCREEN]` artifact segments"*. The documented workarounds
are `--no-ocr`, raising the confidence threshold, or post-filtering with `jq`.

Shipping 1.0 while the differentiating feature's documented remedy is "turn it off or
filter the output yourself" is hard to defend. Needs stability-aware detection, not
another threshold knob — three OCR-quality sprints have already been spent on knobs.

### 4. Valid input crashes

Two known cases from the roadmap: audio-less video dies with a raw ffmpeg error, and
TikTok bytevc1 variants download video-only. A 1.0 should fail with an explanation or
handle the case, not surface a subprocess stack trace.

### 5. The core feature has no real end-to-end test, anywhere

Every model boundary is mocked in the default suite, and CI runs plain `pytest` with
`-m 'not integration and not eval'`. Of 32 test files, exactly **one** `eval`-marked test
runs a real model — and it is OCR-side only. There is **no test, in or out of CI, that
runs real Whisper ASR end to end.**

98.4% coverage measures how much code the mocks touch. It does not tell you the product
works. Before 1.0 there should be at least one smoke test — a few seconds of audio, real
model, asserting non-empty plausible output — even if it runs nightly rather than per-PR.

### 6. The output schema is about to be frozen, and it has a known wart

`TranscriptSegment.confidence` means **two different things**: a negative `avg_logprob`
from ASR, and a 0–1 mean match score from OCR. No validator, no range, documented only as
a comment explaining why merge copies rather than compares it. `IMPLEMENTATION_PLAN.md`
still lists *"should the merge engine surface a unified per-segment confidence?"* as an
open question.

1.0 is the moment that schema becomes a compatibility promise. Fix or explicitly document
it **before** the promise, because afterwards it is a breaking change.

## Tier 2 — GUI and UX

### 7. There is no graphical interface of any kind

No HTML, CSS, JS, templates, static or frontend directory exists. The entire surface is 3
CLI commands (`transcribe`, `transcribe-many`, `serve`) and 4 HTTP endpoints. A Web UI is
listed in Phase 6 as unscheduled.

**The important dependency: a GUI cannot ship on the current API.** Today it is
single-worker, in-memory, unauthenticated, poll-only, JSON-only, with no cancellation. A
web front end over that gives users a page that loses their jobs on restart, cannot be
exposed to a network, cannot cancel, and cannot show progress. So "add a GUI" is really
"harden the API, then add a GUI" (see Tier 3).

Options, cheapest first:
- **Gradio/Streamlit** (the roadmap's suggestion) — fastest to a demo, weakest as a
  product, adds a heavy dependency.
- **A small served page on the existing FastAPI** — no new runtime dependency, reuses
  `/jobs`, and forces the API hardening that is needed anyway. Recommended if a GUI is
  wanted.
- **Desktop app** — best fit for a local-first GPU tool, much the largest effort.

### 8. UX gaps independent of any GUI

- **No progress on a single `transcribe` run.** The rich progress bar exists only in
  `transcribe-many`. A user transcribing a long video sees nothing while a 1.6 GB model
  downloads and inference runs. This is the highest-value, lowest-cost UX fix available.
- **No config file.** `.env` and `OMNI_*` env vars only — no TOML/YAML. The CPU incantation
  is four exported variables.
- **No cancellation** anywhere, CLI or API.
- **Docs are reference-only.** README plus four `docs/*.md`; no tutorial, no CLI reference,
  no API reference, no deployment guide. `docs/plans/` is 23 internal sprint documents —
  developer history that a user should never be pointed at.

## Tier 3 — API v1 hardening (prerequisite for any GUI)

The roadmap already names these: auth, job persistence, cancellation, and `JobRequest`↔CLI
option parity (the API cannot currently set `ui_filter`, `scene_change`, or the LLM
fields). Add: progress reporting, and a decision on SSE vs polling.

Also open per the roadmap: an `errors.py` hierarchy that was designed but never
implemented — everything raises `OmniScribeError`.

---

## Explicitly NOT on the v1.0 path

- **#83 / #84 remote-API backends.** Optional extras. They add a network dependency and a
  credential surface to a tool whose selling point is local operation. Nothing about 1.0
  requires them, and #77 — the only requester — has gone quiet since v0.3.0 fixed the
  install bugs that may have been their actual problem.
- Speaker diarization, content analysis, browser extension, extra platform profiles. All
  are 1.x features; none is needed for the sentence at the top.

---

## Suggested order

1. **Distribution** (Tier 0) — name decision, publish workflow, fix README, correct #77.
   Nothing else matters if users cannot install it.
2. **Robustness + honesty** (Tier 1, items 4–6) — crash fixes, one real ASR smoke test,
   settle the `confidence` semantics before the schema freezes.
3. **OCR noise** (item 3) — the largest genuine engineering effort here, and the one most
   likely to need research rather than implementation.
4. **Single-run progress** (item 8) — small, high user-visible value, independent of
   everything else.
5. **API hardening** (Tier 3) → **GUI** (Tier 2). Only in that order.

Steps 1, 2 and 4 are each small. Step 3 is the real work. Step 5 is the largest scope
decision and the one most worth deferring until you know whether this tool wants users
beyond the command line.
