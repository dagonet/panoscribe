# Release v0.4.0

Tier: T2

## Why 0.4.0 and not 0.3.1

PR #101 split `TranscriptSegment.confidence` into `asr_logprob` + `ocr_confidence`.
That is a breaking change to the JSON transcript format — the `confidence` key is gone
and two new keys replace it. Anything parsing panoscribe JSON output breaks. Pre-1.0
semver puts that in a minor bump.

## What this release carries

- **#100** — Trusted-Publishing PyPI workflow (`publish.yml`), plus packaging fixes:
  PEP 639 license metadata (the SPDX/classifier conflict that would have hard-failed
  the first upload), `py.typed` now shipped, tag/version drift guard.
- **#101** — BREAKING: `confidence` -> `asr_logprob` (negative float, Whisper
  `avg_logprob`) + `ocr_confidence` ([0.0, 1.0]).
- **#102** — corrected the stale Metadata-2.4 claim in `pyproject.toml`.
- **#103** — real-Whisper e2e test behind `@pytest.mark.slow`, plus the opt-in
  `e2e-whisper` CI job (nightly + dispatch), verified green on a real dispatch run.
- Whatever the OCR measurement workstream lands, if it merges before the tag.

Earlier this session, #98 (bootstrap command + gate preflight guard) and #99 (CHANGELOG
rename residue) also landed; both are user-visible enough to mention.

## Hard prerequisite — NOT automatable from here

The publish jobs use Trusted Publishing (OIDC). They will FAIL unless pending
publishers exist. The user must register on **both** sites separately:

| Field | Value |
|---|---|
| Owner | `dagonet` |
| Repository | `panoscribe` |
| Workflow | `publish.yml` |
| Environment | `testpypi` (on test.pypi.org) / `pypi` (on pypi.org) |

The workflow filename is load-bearing — renaming it breaks the trust relationship.

**Do not push the tag until this is confirmed done.** A tag push fires `publish.yml`;
firing it without pending publishers produces a guaranteed-red release run for no
benefit. Preparing the release commit is fine and should proceed regardless — only the
tag waits.

## Known unknown

Whether Warehouse accepts `Metadata-Version: 2.5` (emitted by hatchling 1.32.0) is
unverified. twine 7.0.0 accepts it; that is not proof PyPI does. This is precisely what
the TestPyPI-first design absorbs — a rejection surfaces on TestPyPI before the real
filename is touched. If TestPyPI rejects 2.5, the fix is to pin hatchling to a version
emitting 2.4, not to work around it at upload time.

## Scope

1. `pyproject.toml` — `version = "0.3.0"` -> `"0.4.0"`. This is the literal the
   `guard` job compares against the tag; there is no VCS-derived versioning.
2. `CHANGELOG.md` — a `## [0.4.0]` section. Lead with the BREAKING change and its
   migration note (old key, both new keys, each range), then the publish workflow, the
   e2e test, and the packaging fixes. Add the `[0.4.0]` link reference in the same
   `dagonet/panoscribe` form the rest of the file now uses.
3. Confirm `src/panoscribe/__init__.py` still reads the version via
   `importlib.metadata.version("panoscribe")` — it should need no edit; verify rather
   than assume.

## Verification

- `bash hooks/run-gate.sh` -> PASS. Report actual numbers.
- `uv run panoscribe --version` -> `panoscribe 0.4.0` after a re-sync.
- `uv build` && `uvx twine check --strict dist/*` -> PASSED on both artifacts. Use
  `uvx`, NOT `uv run twine`: the venv's twine 6.2.0 monkeypatches packaging's valid
  metadata list to cap at 2.4 and will falsely reject the 2.5 metadata. `uvx` resolves
  twine 7.0.0, which has no such cap. Delete `dist/` afterward.
- Dry-run the guard logic: tag `v0.4.0` vs pyproject `0.4.0` must match.

## Release sequence (after the PR merges)

Follow `docs/release-process.md`. Tag `v0.4.0` (the repo convention is `vX.Y.Z`, 18
existing tags all use it), push the tag, then watch the `publish.yml` run: guard ->
build -> TestPyPI. Verify the TestPyPI upload landed and is installable before allowing
the real-PyPI job.
